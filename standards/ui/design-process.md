# UI design process and screen patterns

These controls are our policy, informed by the [design sources](sources.md#additions-of-21-november-2026). They define how screens are decided before implementation and which patterns every screen follows. They extend [U01–U16](common.md) without changing them. The Planner (Atlas) proposes; the product owner approves; the Implementer builds the approved packet and cannot redesign it.

| ID | Required control | Check and rejection example | Sources |
| --- | --- | --- | --- |
| UX01 | Decide the design in order: strategy (users, needs, objectives), scope (functions and content), structure (flows and information architecture), skeleton (screens and navigation), surface (visual design). Garrett describes these as dependent planes, not a process; treating them as ordered gates is our policy. | Questionnaire stages 1–7 approved in order. Reject visual work on a screen whose journey is undecided. | [SUI20](sources.md#sui20) |
| UX02 | Record a role-to-capability and a role-to-destination matrix. Hiding a destination is never the access control; the server decides. | Reject a screen that no role reaches, or a role with no first screen. | Our policy; no source prescribes role-based navigation. [U09](common.md) |
| UX03 | Derive every screen from a journey step. Document flows as wireflows that include failure, empty, denied and cancel branches. | Reject a screen that appears in no journey, or a flow with only the success path. | [SUI21](sources.md#sui21) |
| UX04 | Keep information architecture separate from navigation. Use visible navigation with keyword-first labels; do not hide desktop navigation behind an icon or duplicate one menu in two places. Use tabs only for a few parallel views that need not be seen together, in one row. | Reject a hamburger-only desktop menu; two rows of tabs; tabs mixing navigation and in-page views. | [SUI21](sources.md#sui21) |
| UX05 | The product owner approves a clickable prototype before the design packet is frozen. Screenshots of each approved screen and state are stored with the packet as the approval record and become the visual baselines of [UT07](testing.md). The packet, not the screenshots, defines behavior. | Reject a frozen packet with no approved prototype; a baseline changed without the product owner's approval; a screenshot offered as the specification of an action. | [SUI21](sources.md#sui21), [SUI10](sources.md#sui10) |
| UX06 | Data tables serve finding, comparing, viewing or editing one row, and acting on rows. The first column is a human-readable identifier; columns are ordered by importance; sorting, filters and row and batch actions are specified. | Reject a table led by a generated ID; unspecified sort or filter behavior. | [SUI22](sources.md#sui22) |
| UX07 | Forms record why each field is asked. Record when validation runs: on submit by default, inline only for fields where it helps. On error, keep the input, show a summary and a message beside each field in plain words that say how to fix it. | Reject a form that clears input on error, a message that blames the user, or an undecided validation moment. | [SUI23](sources.md#sui23), [SUI08](sources.md#sui08) |
| UX08 | Design every empty state as content: say what the state is and offer the next action. Never show an empty state while data is loading. | Reject "No records" during a load; a blank panel on first use. | [SUI22](sources.md#sui22), [SUI24](sources.md#sui24) |
| UX09 | Give immediate feedback. Show progress for anything over about one second; use determinate progress for long operations. Use skeleton placeholders only for initial loads of content areas. | Reject a frozen screen during a request; a spinner on a multi-minute job; a skeleton inside a dialog. | [SUI22](sources.md#sui22), [SUI24](sources.md#sui24) |
| UX10 | Confirm only destructive or irreversible actions. The confirmation names the object and count; its buttons state the outcome; nothing destructive is the default. Prefer undo where possible. Do not open a dialog from a dialog. | Reject "Are you sure?" with Yes and No; confirmation on routine saves. | [SUI22](sources.md#sui22), [SUI24](sources.md#sui24) |
| UX11 | Distinguish contextual indicators, input validation and notifications of system events. A notification that carries an action stays until dismissed. | Reject a success toast as the only sign of a failed save. | [SUI22](sources.md#sui22), [SUI24](sources.md#sui24) |
| UX12 | Record whether the project adopts or adapts a design system. The default base is shadcn/ui components on Tailwind CSS, copied into the repository, with one primitive library pinned. The builder is given the component source, not asked to recall it. | Reject a second component library added for one screen; components generated from memory of an API. | [SUI25](sources.md#sui25) |
| UX13 | Define tokens for color, spacing, type and motion in the Design Tokens format, with a limited spacing scale on one base unit and a type scale. Record contrast evidence for text and controls. Do not signal by color alone. | Reject an arbitrary pixel value or hex color in a component; a status shown only by color. | [SUI17](sources.md#sui17), [SUI26](sources.md#sui26), [SUI05](sources.md#sui05) |
| UX14 | Before freezing, an evaluator other than the author reviews the prototype against usability heuristics and records findings. Design tools, including AI generators, may be used to explore; their output is never the source of truth and none may receive project content under terms that train on it without recorded approval. | Reject the author's self-review as the evaluation; a hosted generator's export adopted as the design. | [SUI02](sources.md#sui02), [SUI27](sources.md#sui27) |

## Who decides

| Decision | Proposes | Decides |
| --- | --- | --- |
| Roles, journeys, scope | Atlas, from the product owner's answers | Product owner |
| Navigation, screens, states, patterns | Atlas, applying UX04–UX11 | Product owner, on the prototype |
| Design system, tokens, look | Atlas, applying UX12–UX13 | Product owner |
| Change to an approved screen or baseline | Anyone, as a recorded change | Product owner |

The frozen result is the [design packet](design-packet.template.json), which `ui-standard design` validates structurally. That validator does not check UX06–UX14; they are review items.
