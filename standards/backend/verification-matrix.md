# Backend rule-to-verification matrix

Status: rule/control specification with executable reference coverage. The [reference implementations and common acceptance suite](../../reference/README.md) exercise the selected HTTP/PostgreSQL bindings; [adoption](adoption.md) identifies input/evidence validation and the remaining external trust/dispatch boundary. A passing reference does not automatically validate every conditional feature or release a v1 standard.

The requirements remain in [common rules](common.md) and [testing rules](testing.md). Their IDs and source attribution are unchanged. This matrix defines proposed verification bindings, owners, failure handling, and rejection examples. These bindings are our engineering policy; the cited authors do not collectively mandate this exact process.

## Read the matrix

- **Planner** records applicability, expected behavior, contracts and the check plan before dispatch.
- **Implementer** writes code and meaningful tests, runs the required local checks, and supplies factual results before submission for acceptance. A draft PR can exist earlier; it is not a verified handoff.
- **CI** executes required checks in a clean, controlled environment and preserves candidate-bound reports.
- **Independent Reviewer** evaluates requirements coverage and semantic/design concerns, including approved applicability. It cannot replace missing execution evidence with an opinion.
- **Coordinator** validates evidence and controls workflow transitions. It does not rely on an implementer's success statement.
- **Release owner / Operations** handle checks that apply to packaging, release or deployed behavior.

Gate names are the existing [G0-G5 definitions](testing.md#gates). G0 blocks dispatch; G1 blocks a verified developer handoff; G2 blocks CI acceptance; G3 blocks independent acceptance. A failure at G1-G3 prevents task completion. G4 blocks release readiness and G5 blocks deployment acceptance when those stages are in scope. Task completion follows the [Definition of Done](definition-of-done.md#acceptance-boundary): integration is required, deployment only when included in the task.

An ordinary failed check returns to implementation within the configured repair budget. An unavailable dependency, missing authority, unresolved decision or exhausted budget is `blocked`. Neither is `passed`. A repair that changes the candidate requires updated checks and review for that candidate; a relevant base change also requires new integration evidence.

## Check methods and trust

**Static/configuration checks** can enforce selected syntax, dependencies and configuration. **Executed behavior checks** exercise an actual application or dependency. **Independent review** handles design justification and semantic coverage that tooling cannot reliably decide. A rule can require all three; a linter or a second LLM alone cannot prove intended behavior.

The adopting project binds every applicable row to actual paths, pinned tools, commands, reports and the trusted runner/reviewer. Expected outcomes come from accepted requirements, not implementation output. Verification configuration, acceptance fixtures and exception approvals need independent change review and appropriate repository protection. A candidate cannot authorize weakening the controls that accept it.

## Common backend controls

The rejection examples describe violations to demonstrate safely in a disposable test environment when implementing a new control, or when a critical invariant changes. Concrete reference/unit results are recorded separately; a matrix row alone is not execution evidence or an instruction to mutate every application on every PR. Preserve a failure-before/success-after result or an explained equivalent as required by T07. Never use production secrets or user data in these demonstrations.

## Testing and evidence controls

These controls apply to the applicable suites/checks selected for a task. A documentation-only task does not need invented application tests. A behavior change cannot be relabeled documentation-only to avoid verification.

## Applicability and exceptions

For each rule, the Planner records the feature/requirement that makes it applicable and the verification boundary. The Reviewer validates material/high-risk selections. Conditional clauses can be N/A while the rest of a rule remains required: a public stateless endpoint can omit tenant/migration cases, but still needs its public-access decision, validation and meaningful verification.

An N/A entry needs the rule/clause, evidence of absence of the feature, rationale and independent review. Lack of a runnable test environment is `blocked`, not N/A. A failed test cannot be made N/A by the Implementer.

An exception uses the existing [exception policy](README.md#normative-meaning): rule, rationale, risk, compensating control, accountable independent reviewer and expiry/review date. It must appear in the project and task evidence. A changed feature or baseline requires re-evaluating affected applicability/exception decisions.

## Evidence record and completion

The existing [verification record](templates/verification-record.template.json) indexes evidence; it is not proof of execution. The adopting project's check records must identify the rule, applicable acceptance cases, actual command/check identity, runner, candidate/base revision, report references, result and counts when tests execute. Attach artifact digest where packaging/deployment is checked. Do not invent test counts for linters or reviews.

The Coordinator evaluates [D01-D10](definition-of-done.md), not an overall badge. A failed, blocked, unreported, stale or unauthorizedly skipped applicable required check prevents the corresponding transition. Independent semantic review is still required where defined; matching IDs and green tooling alone do not establish product correctness.

See [baseline readiness](baseline-readiness.md) for what is still missing before this specification becomes a reusable, validated standard.
